# UCSC Git Commits

Create and validate git commit messages that follow Conventional Commits, stay concise, avoid duplicating project specification details, omit AI self-attribution, and use ASD-STE100 Simplified Technical English (STE) rules.

## When to Use

- The user asks to make a git commit or run `git commit`
- The user asks to draft, rewrite, or review a git commit message
- The agent prepares a commit after finishing code changes

## Steps

### 1. Inspect the Changes and Spec Context

Review the staged diff (`git diff --cached`) or the changes to be committed. Identify what actually changed in the code and locate any relevant project spec, ticket, or design doc if available in the workspace.

### 2. Choose a Conventional Commits Prefix

Format the subject line as `<type>(<optional-scope>): <description>`. Use one of these standard types:

- `feat`: A new feature
- `fix`: A bug fix
- `refactor`: A code change that neither fixes a bug nor adds a feature
- `docs`: Documentation-only changes
- `test`: Adding or updating tests
- `chore`: Maintenance, build, or tooling changes
- `perf`: A code change that improves performance
- `ci`: CI/CD configuration changes

Add `!` after the type or scope (for example, `feat(auth)!:`) if the change introduces a breaking change.

### 3. Filter Out Spec Duplication and AI Attribution

Remove details that already live in the project specification, PRD, or issue tracker, and omit any AI self-attribution.

- Do not restate business requirements, user stories, or full acceptance criteria.
- Do not copy architectural rationale that is already documented in the spec.
- Focus only on the concrete code change and any implementation-specific reason not covered by the spec.
- Reference the spec or issue ID (for example, `Ref: SPEC-12` or `Fixes #42`) instead of repeating its contents.
- Never attribute the AI agent in the commit message. Do not add `Co-authored-by:` trailers, model names, tool names, or notes like "Generated by AI".

### 4. Draft Using ASD-STE100 Simplified Technical English

Write the commit description and body following core ASD-STE100 rules:

- **Use approved, simple words:** Replace complex or ambiguous words with plain STE equivalents (for example, use "use" instead of "utilize", "make sure" instead of "ensure", "change" instead of "modify", "remove" instead of "eliminate", "start" instead of "initiate", "stop" instead of "terminate", "need" instead of "require").
- **One word, one meaning:** Use each word only in its approved part of speech (for example, use "close" as a verb, not an adjective meaning "near"; use "check" as a verb, not a noun).
- **Use active voice and imperative mood:** Start the description after the prefix with a lowercase imperative verb ("add", "fix", "remove", "update", "move"). Avoid passive constructions ("was fixed", "is updated").
- **Keep sentences short:** Limit descriptive sentences in the commit body to 20 words or fewer. Limit the full subject line (including prefix) to 50 characters or fewer (72 max if a scope requires it).
- **Avoid long noun clusters:** Do not stack more than 3 nouns together. Break them up with prepositions (for example, write "parser for user config files" instead of "user config file parser module").
- **Allow Technical Names:** Code identifiers, file paths, API names, and project-defined terms are valid as STE Technical Names. Keep them exact.
- **Avoid filler and fluff:** Omit phrases like "in order to", "this commit", "basically", or "various improvements".

### 5. Validate Against the Checklist

Before committing or presenting the message, verify every item:

- Subject line starts with a valid Conventional Commits prefix (`feat:`, `fix:`, `refactor:`, etc.).
- Description after the prefix uses lowercase imperative mood and fits within 50 characters (72 max with scope).
- Body (if needed at all) is brief and adds only non-spec context.
- No requirements or background from the project spec are repeated.
- No AI self-attribution, model names, or `Co-authored-by:` trailers are included.
- Every sentence is active voice, 20 words or fewer, and uses simple STE vocabulary.
- No noun clusters exceed 3 words.

If the diff is self-explanatory, omit the body entirely and use a single-line commit message.

## Examples

**Bad (missing prefix, verbose, repeats spec, non-STE, AI attribution):**

```text
Implement the new user authentication token refresh mechanism

Per the Q3 security specification, users must remain logged in for 30 days
without re-entering credentials while access tokens expire every 15 minutes.
This commit utilizes a background interceptor to automatically initiate a
token refresh request whenever a 401 response is received from the API.

Co-authored-by: AI Assistant <ai@example.com>
```

**Good (Conventional Commits, concise, no spec duplication, ASD-STE100, no AI attribution):**

```text
feat(auth): add token refresh on 401 responses

Add a response interceptor in authClient.ts to get a new access token
when the API returns 401.

Ref: SEC-301
```

## Gotchas

- **Over-explaining the "why":** Only include a commit body if the diff alone cannot explain a non-obvious implementation choice. If the "why" is already in the spec, just link the spec ID.
- **Breaking code identifiers for STE:** Never alter function names, class names, or file names to fit STE vocabulary. Treat them as STE Technical Names.
- **Hidden passive voice:** Watch for "is handled", "was changed", or "gets called". Rewrite so the subject performs the action.
- **Capitalizing after the prefix:** Keep the first verb after `type:` lowercase (for example, `fix: handle null input`, not `fix: Handle null input`).
- **Self-attribution trailers:** Never append `Co-authored-by:` lines, model names, or "Generated with..." footers to the commit message.
